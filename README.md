# 即梦积分管家

> 多人共用 AI 积分时，钱会在没人看的时候漏掉。

一个面向团队的**即梦（Dreamina）积分监控工具**：员工端浏览器扩展静默采集，管理台集中呈现余额、消耗、归属与到期，并把积分折算成人民币。

---

## 为什么做这个

一个七八人的内容团队，用同一个 AI 生成平台买会员、按积分扣费。管理方式是「行政统一买会员，谁要用谁登」。

问题出在积分的使用形态上：

- **预付费**——钱先花出去，额度慢慢消耗
- **按量消耗**——扣费分散在每次生成里
- **分批到期**——不同批次有效期不同，过期即清零
- **分散在多个账号**——个人账号、团队共享额度并存

结果就是：**没有人知道还剩多少、什么时候到期、谁在用什么。**

而传统的成本管理手段在这里是失效的——AI 积分的消耗不会出现在任何一张发票上，也不会在月度报表里留下痕迹。

这个工具想解决的就是这一件事：**让原本隐形的成本变得可见。**

## 核心能力

### 1. 员工端无感采集

浏览器扩展（Chrome MV3）只做一件事：读取即梦页面上的积分余额与流水，上报到服务端。

- 员工照常用即梦，**不需要改变任何操作习惯**
- 只读，不生成、不调整额度、不操作成员
- 不申请 Cookie 权限，不上传登录凭据、提示词或素材
- 断网时本地排队，联网后补传

### 2. 管理台总览

管理者打开一个网页，就能看到：

| 维度 | 内容 |
|---|---|
| 余额与到期 | 每个部门、每个账号还剩多少、什么时候到期 |
| 归属与操作 | 每个员工名下消耗 vs 本人实际操作 |
| 借用关系 | 谁用了别人的额度（扣费账号与实际操作人分开记录） |
| **浪费与临期** | **已经到期损失多少钱、还有多少钱快到期** |

### 3. 积分折算成人民币

单价按**积分来源分别计算**，这是准确性的关键：

| 来源 | 计价方式 |
|---|---|
| 订阅会员积分 | 该账号套餐月费 ÷ 每月实发积分（取续费原价） |
| 充值购买积分 | 固定 ¥0.10/分 |
| 每日登录赠送 | **按 0 成本**（本来就没花钱） |

> 赠送积分如果算进去，等于把「没浪费」算成「浪费」。

折算后，管理者看到的不再是「还剩 71,680 分」，而是「还剩约 5,260 元」。**数字一旦变成钱，事情的性质就变了。**

### 4. 归属历史不回溯

人员或部门变动时，**不会倒算此前的消耗记录**。

归属按流水发生当时已登记的映射保留，未确认的历史单独标注；调整归属只影响此后的记录。

## 一个真实的发现

在真实使用中，这个工具跑出的第一份数据揭示了一个反直觉的结论：

> **共享额度的浪费远高于个人账号。**

个人账号的额度是自己的，用完就没了，使用者会下意识地盯着；而团队共享额度是公共池子，每个人都能用，于是每个人都默认「别人会用」「还早」「不差我这一次」。

**一个人的资源会被珍惜，一群人的资源会被浪费。** 这不需要谁犯错，只需要没有人负责。

这也是这个工具真正想解决的问题——**不是记账，而是把责任显性化。**

## 架构

```
┌─────────────────────┐      ┌──────────────────────┐
│  浏览器扩展 (MV3)    │─────▶│   服务端 (Node 22)    │
│  读取即梦页面余额    │ HTTP │   HTTP + SQLite      │
│  只读、无感、可补传  │      │   采集接口 + 管理 API │
└─────────────────────┘      └──────────┬───────────┘
                                        │
                             ┌──────────▼───────────┐
                             │   管理台 (React/Vite) │
                             │   总览 / 归属 / 流水  │
                             └──────────────────────┘
```

- **运行时**：Node.js 22（内置 `node:sqlite`，无外部数据库依赖）
- **前端**：React + Vite + Semi UI
- **扩展**：Chrome Manifest V3
- **依赖策略**：尽量使用标准库，仅在有明确缺口时引入依赖

## 快速开始

```bash
# 依赖
npm install

# 启动服务端（默认 127.0.0.1:4318）
npm start

# 开发模式（前端热更新）
npm run dev
# 另一个终端
npm run preview:web

# 构建前端产物
npm run build

# 运行测试
npm test
```

首次启动会在 `.local/` 下生成管理员密钥（权限 0600），**不会写入日志**。

### 配置采集端

1. 管理台 →「接入设置」→ 添加采集端，选择员工
2. 下载该员工的专属扩展包（含预配置的 endpoint 与作用域 token）
3. 员工在浏览器中加载扩展
4. 员工正常使用即梦，数据自动上报

## 设计原则

- **只读采集**：扩展只读页面数据，不做任何写操作
- **归属不等于责任**：账号归属人 ≠ 实际操作人，两者分开记录
- **不猜数**：平台没返回的价格就标注「未获取」，不填零、不推算
- **先只读取证，再决定是否写入**：数据核查类操作先确认异常再修改
- **保留不确定性**：估算值明确标注为估算，不用看起来精确的假数字

## 适用范围与边界

**适合**：多人共用按积分计费的 AI 平台、需要按人/按部门核算成本、积分存在到期风险的团队。

**不适合**：单人使用场景（直接看平台后台即可）；需要绕过平台限制或自动化操作账号的场景。

**已知边界**：

- 平台接口变化可能导致采集适配需要更新
- 团队共享额度的单价若平台下架，只能按同级个人会员单价估算，需人工复核
- 当前仅适配即梦；同一套「采集余额 → 归属到人 → 折算金额 → 盯到期」的思路可以移植到其他按积分计费的平台
